# Independent Forensic Audit — TriHex

**Audit date:** 2026-09-15  
**Scope:** current checkout at `bca2ed3`; source, all committed tests and benchmark scripts, TypeScript build, and independent bounded topology checks. No production source was changed. Temporary audit programs were created only under `/tmp` and are not part of this repository.

> **Remediation update:** The P0 hex-neighbour implementation described below was corrected after this baseline audit. The current implementation exposes three true triangular edge neighbours through `getCellNeighbors`/`cellDisk`, deprecates the misleading hex compatibility names, and adds a shared-edge property check. The remaining routing, Redis, topology, database, rasterization, and scalability findings remain open.

## EXECUTIVE VERDICT

**FAIL — NOT PRODUCTION READY**

TriHex has a real icosahedral triangular 1:4 encoding and a valid signed-positive ID layout for its supported resolutions. It does **not** implement the claimed hexagonal Voronoi dual: every one of 480 reported neighbour links at exhaustive resolution 1 failed the geometric shared-edge test, while the real triangular-cell edge degree is three, not six. Its globally six-regular graph is an artificial centroid-offset graph, not the dual or adjacency graph of the stored triangles. The dispatch and Redis code are useful prototypes, but lack sequencing, atomic offline removal, expiration cleanup, topology construction, a routing implementation, a real Redis integration test, and capacity evidence. This must not be used as a ride-hailing spatial foundation.

## 2. What Is False or Misleading

* The README claim that the aggregation layer supplies “uniform 6-way hexagonal symmetry” and the tests’ “Voronoi dual” wording are false for the stored triangular cells. Six returned IDs do not share stored-cell edges with the origin.
* The specification claim of a globally uniform, regular hexagonal dual on an icosahedron is mathematically incompatible with a spherical triangulation having 12 degree-five vertices. The code hides this singularity by creating non-adjacent offset links.
* “100% reciprocal symmetry” is not evidence of Voronoi validity: the artificial graph is reciprocal, but its links are not triangle adjacencies.
* “zero false-positive leaks” is overstated. The dense interval is correct **only among same-face, same-target-resolution descendant IDs**. A geographic region, line, or polygon crosses face ranges and cannot generally be represented by one parent interval; no SQL plan or PostgreSQL run exists.
* The README/specification says topology is in 12 ID bits, but current code deliberately ignores `topoCluster` in packing and stores it in a process-local map. The serialised ID does not carry topology at all.
* “Eliminates ghost drivers caused by process crashes or network split-brain” is false. Lua atomicity cannot repair a request that never reaches Redis, cannot prevent a later stale request, and does not remove expired position members from a set.
* The benchmark claims are microbenchmark figures from five reused coordinates / one reused cell, without warm-up, GC control, allocation accounting, percentiles, routing, Redis, network, or concurrency. They are not fleet capacity evidence.
* The massive test calls “1,000 concurrent” searches but awaits each search inside a `for` loop. It is sequential.

## 3. Critical Findings

### P0 — invalid “hexagonal Voronoi dual”

```text
Severity: P0
Component: Hex dual / spatial adjacency
File: src/hex-dual.ts
Function: getHexNeighbors; getHexDualBoundary; hexRing
Claim: Six returned cells are equidistant Voronoi neighbours of every triangle globally.
Actual behavior: The function translates a triangle centroid by fixed face-plane offsets, reprojects it, and returns six cells. Those cells are not the three edge-adjacent stored triangles and do not construct a Voronoi cell. The boundary is merely six returned centroids in offset order.
Evidence: Exhaustively enumerate all 80 cells at resolution 1 and compare the three radial-projected boundary vertices of each returned ID. All 480 reported directed links shared zero stored edges; exhaustive actual edge adjacency degree was 3 for every stored triangle. hexRing(id,2) had 22 cells for all 80 res-1 cells, not 19.
Production impact: candidate expansion, surge diffusion, GeoJSON “hexagons,” and any topology/routing logic using these links can skip cells, cross barriers, and have invalid coverage.
Reproduction: node /tmp/geo.js (program reproduced in section 9) after npm run build.
Required fix: remove the hex/Voronoi production claim. Either expose correct triangular edge adjacency, or design a genuine spherical dual with explicit 12 pentagonal singularities and prove seam topology.
```

### P1 — stale GPS events can move a driver backwards; removal is non-atomic

```text
Severity: P1
Component: Dispatch / Redis state
File: src/dispatch.ts
Function: MIGRATE_DRIVER_LUA; updateDriverPosition; removeDriver
Claim: Atomic migration eliminates ghost drivers and supports production real-time updates.
Actual behavior: Lua accepts any supplied old/new cell and never compares updatedAt, a version, or a sequence token. A late A(t=1) request after B(t=2), passed with oldCell=B, removes B and restores A. removeDriver executes SREM then DEL as separate commands. Cell set TTL is refreshed by any write, while individual member expiry is absent.
Evidence: Lua only SREM/SADD/EXPIRE/SET; payload updatedAt is not read. updateDriverPosition trusts optional oldCellId. removeDriver has two awaits.
Production impact: stale positions, ghost set members, incorrect candidate selection, unbounded stale-member amplification in active cells, and offline-race resurrection.
Reproduction: send B then delayed A with oldCellId B; inspect cell sets. Interrupt between removeDriver's SREM and DEL.
Required fix: server-side monotonic sequence/CAS in one Lua script; keep authoritative current cell/version; atomic offline tombstone/removal; per-member expiry strategy or periodic reconciliation; idempotency and failover tests.
```

### P1 — all keys for a city are forced to one Redis Cluster slot

```text
Severity: P1
Component: Redis clustering / hotspot scalability
File: src/dispatch.ts
Function: formatCellKey; formatDriverKey
Claim: “cluster-safe” city hash tags support scale.
Actual behavior: `{cityId}` is the hash tag for every cell and every driver in that city. Redis Cluster therefore places an entire megacity on one primary shard. Candidate lookup performs serial SMEMBERS calls per cell and serial GET calls per candidate.
Evidence: key formats use `{${cityId}}`; the query loop awaits `smembers` per cell and `getDriverPosition` per candidate.
Production impact: city-sized hot shard, no intra-city horizontal scaling, network round-trip amplification, and poor p99 under hotspot load.
Reproduction: compute Redis Cluster slots for two different `{lagos}` keys: they are identical.
Required fix: shard by stable spatial prefix/partition (and design cross-slot retrieval), batch/pipeline/multi-get, impose member/candidate limits, and load test an actual Redis Cluster including failover.
```

### P1 — routing, topology, candidate recall, and ETA correctness are absent

```text
Severity: P1
Component: Routing/dispatch
File: src/dispatch.ts; src/network-metric.ts
Function: RouteCostProvider; findCandidates; TopologyPartitionRegistry; effectiveDistance
Claim: Road-network awareness and optimal mobility dispatch.
Actual behavior: Routing is an optional interface. Topology is a manually-populated process-local map; unregistered cells all share cluster 0. Candidate collection stops after a small k-disk / count threshold, ranks geodesically, routes only top 5 by default, and silently substitutes straight-line ETA if routing rejects.
Evidence: no OSRM/Valhalla/GraphHopper client, road graph, traffic feed, partition builder, persistence, or routing ground truth is in the dependency tree or source.
Production impact: no reachability guarantee; top-5 routing finds only the best of its prefilter, not the global best reachable driver. River, bridge closure/reopening, one-way, turn restriction, traffic, airport and asymmetric network behavior are unmeasured.
Reproduction: configure a mock provider in which the sixth geodesically closest driver has the best route ETA; it can never be chosen under default tier2Limit=5.
Required fix: integrate a real routable graph/ETA service; define topology semantics and lifecycle; use route-table/batched ETA candidate expansion; publish scenario-based Recall@K and failover/timeout policy.
```

### P2 — public low-level functions bypass ID validation and packing masks bad inputs

```text
Severity: P2
Component: ID/API boundary
File: src/triangle-quadtree.ts; src/index.ts
Function: packTriHexId; cellToChildrenRange; getHexNeighbors
Claim: strict structural validation.
Actual behavior: packTriHexId masks face/resolution/morton rather than rejecting out-of-range fields; public wrappers for children range and neighbour functions do not validate IDs. Low-level exports permit malformed IDs to be transformed into valid-looking colliding IDs.
Evidence: bitwise masks in packTriHexId and direct forwarding wrappers.
Production impact: callers that use public packing or untrusted IDs can create collisions or force undefined geometries; TypeScript types do not validate runtime values.
Required fix: validate every public entry point; separate unsafe/internal packing from validated API; add malformed-ID property tests.
```

### P2 — rasterization is sampled planar lat/lng, not exact supercover/polygon coverage

```text
Severity: P2
Component: Rasterization
File: src/rasterization.ts
Function: lineStringToCells; polygonToCells
Claim: zero-gap supercover and arbitrary polygon fill.
Actual behavior: lines use linear latitude/longitude interpolation and a radius approximation; polygons use degree scanlines and sample points. It has no geometric cell/polygon intersection test, holes, multipolygons, or self-intersection handling.
Evidence: interpolation and scanline sampling at fixed degree steps; API accepts only one coordinate array.
Production impact: false negatives/overcoverage near high latitudes, face seams, thin polygons, holes, and complex input; synchronous loops can block an API worker up to the guard.
Required fix: implement spherical segment/cell intersection and robust polygon clipping/fill, model GeoJSON polygon topology, bound/chunk work, and test reference fixtures.
```

## 4. Mathematical Verdict

| Subsystem | Verdict | Basis |
|---|---|---|
| Icosahedron vertices/faces and radial face projection | PARTIAL | 12 normalized regular-icosahedron vertices and 20 face tuples are present; forward/inverse projection is empirically stable. No independent exhaustive coverage/overlap proof was supplied. |
| Coordinate conversion | VERIFIED WITH LIMITATIONS | Projection inverse error is small. Cell quantization is intentionally large at coarse levels and was mislabeled as round-trip in tests. Boundary tie-break is source-order dependent, not specified as a stable cross-platform policy. |
| 1:4 triangular hierarchy | PASS | For valid per-face Morton IDs, each two-bit digit gives four children and one parent. Geographic face-boundary ownership remains a separate seam issue. |
| Morton interval arithmetic | PASS | Same-face, same-target-resolution descendants occupy the numeric interval. This is an ID-prefix theorem, not a general spatial-query theorem. |
| 63-bit layout/uniqueness | VERIFIED WITH LIMITATIONS | Valid generated `(face,res,morton)` tuples are injective in supported ranges. Pack masking makes unsafe malformed input collisions possible; PostgreSQL/Prisma was not exercised. |
| Hexagonal dual | FAIL | It is neither the dual of the represented triangles nor a globally regular hexagonal tiling. |
| Global k-ring formula | FAIL | Exhaustive res-1 disk size was 22 rather than 19; 120 cells at resolutions 2–6 also deviated. |

## 5. Spatial Index Verdict

* **Coordinate conversion:** VERIFIED WITH LIMITATIONS; valid input checks live only on `latLngToCell`, and geographic boundary ownership is source-order first-hit.
* **Cell assignment/hierarchy:** PASS for encoded per-face triangular subdivision, not independently proven global coverage.
* **Morton ordering:** VERIFIED WITH LIMITATIONS; exact descendants only, with face and resolution embedded above Morton bits.
* **Cell boundaries:** PARTIAL; triangular boundaries exist, but no seam equality/edge matching test exists in the suite.
* **Neighbours/k-rings/hex geometry:** FAIL.
* **Rasterization:** PARTIALLY CORRECT for simple sampled paths/areas; NOT VERIFIED for required geospatial cases.
* **Compaction:** VERIFIED WITH LIMITATIONS for valid uniform descendant sets in committed tests; no malformed/large-set complexity evidence and output ordering is unspecified.

## 6. Routing Verdict

* **Topology model:** NOT IMPLEMENTED as a road graph; mutable process-local labels are not reachability.
* **Candidate generation:** PARTIALLY IMPLEMENTED; radius defaults 1→3, repeats full disks for each radius, stops as soon as raw IDs reach 50, then routes at most 5.
* **Candidate recall / global optimality:** NOT TESTED. Top-K filtering cannot establish global optimum.
* **ETA approximation:** PLAUSIBLE BUT UNPROVEN only as a Haversine/speed fallback; it is not an ETA model.
* **Routing integration:** INTERFACE ONLY.

## 7. Redis / State Management Verdict

**FAIL for production use.** There is no Redis package or integration environment; tests use an in-process mock. Lua makes one submitted migration atomic only when all three keys share a slot. It provides no ordering/idempotency, per-member TTL, reconciliation, crash-before-request recovery, failover behavior, or cluster load evidence. City hash tags deliberately create a hot single-city slot.

## 8. Database Verdict

**UNPROVEN.** There is no PostgreSQL dependency, schema, migration, Prisma client, SQL execution, `EXPLAIN ANALYZE`, index size/depth, bloat, write-amplification, or concurrent workload test. Numeric ID order preserves face/resolution/Morton fields, but that alone says nothing about index selectivity or city-scale range scans.

## 9. Performance Verdict

### Microbenchmarks

The committed benchmark runs 100,000 iterations against five repeated coordinates and one repeated cell, returns are unused, and it has no warm-up/statistical protocol. It only measures local TypeScript function throughput.

### End-to-end benchmarks

No end-to-end benchmark exists. The “massive” test is an in-memory single-process, sequential loop and supplies no Redis CPU/latencies, event-loop lag, routing calls, network traffic, database writes, regional failure, 50k-hot-cell, or multi-worker measurement. Its own phase-3 text says “concurrent” but awaits every query serially.

The measured system therefore cannot support the requested workload claim.

## 10. Scalability Verdict

> Can this implementation actually support 2M online drivers and 20K+ searches/sec?

**UNPROVEN.** The first known bottlenecks are a single city Redis slot, serial fan-out, `SMEMBERS` of unbounded hot sets, and routing fan-out. There is no valid scaling experiment from which worker, Redis, routing, memory, bandwidth, or tail-latency requirements can be derived.

## 13. What I Would Keep

* The compact face/resolution/Morton representation for a **triangular per-face hierarchy**.
* Parent/descendant prefix arithmetic, with an explicit same-face/same-resolution contract.
* Strict finite/bounded validation in `latLngToCell` and canonical BigInt hex serialization.
* The route-provider abstraction, but only as an integration seam—not as evidence of routing.

## 14. What I Would Rewrite

* Replace `hex-dual.ts` and all downstream hex/ring/hex GeoJSON claims.
* Replace mutable global topology labels with a versioned, persistent road-network component.
* Rewrite state migration around authoritative versioned positions and atomic lifecycle transitions.
* Rewrite candidate retrieval for bounded, batched, shard-aware expansion and then a real routing/ETA stage.
* Replace sampled rasterization with robust spherical/geometric operations.

## 15. Production Architecture Recommendation

| Layer | Recommended design |
|---|---|
| Spatial Index | Use a vetted DGGS (H3/S2) or retain only TriHex’s explicitly triangular hierarchy after formal seam proof; use multiple covering cells/ranges for arbitrary regions. |
| Topology | Versioned road graph derived from routing data; never encode mutable reachability in spatial IDs. |
| Candidate Retrieval | Regional spatial shards, bounded cell lists, streaming/pipelined reads, availability/version filtering, adaptive expansion. |
| Routing | Operate OSRM/Valhalla/GraphHopper or a validated commercial service with matrix batching, timeout budgets and regional failover. |
| ETA Prediction | Learned/calibrated ETA using traffic, road class, turn restrictions and supply state; monitor calibration. |
| Dispatch Optimization | Retrieve a high-recall route-feasible pool, route/matrix it, then optimize ETA, acceptance, fairness and assignment constraints. |
| State Management | Durable event stream plus Redis regional materialization; monotonic device/server sequence, idempotency, tombstones, TTL reconciliation, and shard rebalancing. |
| Observability | Per-city/shard hot-key telemetry, stale-member rate, update reordering, recall sampling, routing timeout/error, candidate funnel and p50/p95/p99.9 SLOs. |

## 17. Final Go / No-Go Decision

> **Would you personally sign off on this code as the spatial foundation of a ride-hailing platform serving millions of users?**

**NO**

The claimed neighbour topology is geometrically invalid, and the required routing, recall, distributed-state correctness, database, and scale evidence are absent. The safe disposition is prototype/research only until the checklist above is completed.
